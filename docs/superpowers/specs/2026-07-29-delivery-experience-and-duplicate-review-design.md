# 交付体验与技术文件比对优化设计

## 目标

优化 Windows 交付版本的日常使用体验，不改变商务审核、技术暗标格式检查和 Markdown 结果文件的业务边界。

## 模型设置

- 用户在 API 设置中输入 API Key 并保存时，程序始终将其保存到操作系统凭据管理器。
- 服务地址、模型名称和超时时间继续保存到应用配置文件；API Key 不写入配置文件、任务文件或报告。
- API Key 输入框留空时，保存其他模型设置不得删除已保存的密钥。
- 仅“清除当前密钥”会删除系统凭据和当前进程中的密钥。
- 移除“保存到系统凭据管理器”复选框以及“本次使用”说明，避免用户误以为保存后仍会丢失密钥。

## 任务界面

- 顶部步骤条由任务阶段驱动：编辑时高亮“添加文件”；预检完成或审核中高亮“批量审核”；完成时高亮“查看结果”。已经完成的步骤显示完成状态。
- 在预检、审核和完成阶段，状态与结果区域放在文件选择区之前，使用户打开页面首先看到当前进度或结果。
- 审核完成或失败后提供“重置任务”。它只清空前端的当前任务、文件选择和预览，回到添加文件步骤。
- 重置不得调用现有 `clear_job`，因为该命令会删除任务目录及其 Markdown 结果。已生成报告继续保留在原结果目录。

## 审核结果文本

- 商务审核结果使用“商务审核说明”“商务审核结果”等业务名称，不出现 `tender-review-skill`。
- 技术暗标结果使用“技术暗标格式检查”等业务名称，不出现 `word-format-checker`。
- 内部提示、依赖路径与运行日志可以保留真实工具名，便于排障；面向用户的 Markdown 结果及其预览不得包含这些实现名称。

## 技术文件比对

### 范围

- 只比较已关联的技术暗标 DOCX；少于两份时明确说明未执行比对。
- 不使用模型，全部在本地完成。

### 算法

- 按已提取的文本块比较两份技术文件，而不是将整篇文件转成词项集合。
- 每个文本块去除空白、统一大小写和 Unicode 表示后，与另一份文件的每个文本块做最长公共连续片段匹配。
- 仅保留长度不少于 12 个规范化字符的连续重复片段；短词、单个术语和散落词项不会生成结果。
- 同一文件组合的相同片段去重，并按片段长度从长到短展示。
- 不尝试识别改写、同义替换或语义相似内容，避免在投标审核中扩大误报范围。

### Markdown 输出

- 没有满足阈值的连续片段时，结论为“未发现需重点复核的连续重复内容”。
- 有结果时，每个文件组合展示匹配片段数和表格：重复片段、技术文件 A 位置、技术文件 B 位置、人工复核提示。
- 文件位置使用已提取文本块的行号和结构路径；不再输出词项相似度、共享词项数或由单个词推断的“位置”。
- 保留“结果用于人工复核，不直接认定围标、串标或废标”的说明。

## 测试

- Rust：保存空 API Key 时保留凭据；清除操作删除凭据；连续片段比对忽略短公共词、能定位达到阈值的片段；Markdown 不泄露实现名称。
- 前端：保存模型设置默认要求持久化；步骤条随阶段变化；完成后重置回编辑状态且不调用 `clearJob`；预览文本不包含实现名称。
